## Outcome

On first boot the API generates a VAPID key pair into `~/.config/ogm/env/ogm-api.vapid.json` (0600) if absent; a browser can register a push subscription, list and mark notifications, and hold an SSE stream that resumes from `Last-Event-ID`; a `notify` event on the in-process bus (`build.done`, `job.started`, `intake.report`) or a `POST /internal/notifications/emit` from another service becomes one notification row per recipient, one SSE frame to each open stream, and one Web Push per subscription, with dead subscriptions pruned.

## Context and evidence

E01-16 and spec §5.22: browser push plus in-app status, no email or SMS fallback, no vendor spend; Web Push with self-generated VAPID keys is free; the three triggers (finished builds, queued changes starting, intake reports) come from the architecture doc and C2 §5. E11-6: the Netlify proxy may cut long SSE streams, so the stream must resume cheaply and the push path is the one that reaches a closed phone. E11-10 and D-HOSTING: secrets live under `~/.config/ogm/env/` (0600); the VAPID private key is one of them and is generated by the API, not typed by Kevin. Resolved: the iOS home-screen-install constraint is accepted (spec §5.22); lock-screen content is minimal.

## Scope

- Tables `push_subscriptions(id, user_id, endpoint UNIQUE, p256dh, auth, expiration_time, created_at, last_ok_at, failures)` and `notifications` (the `Notification` contract row).
- `services/api/src/notify/vapid.ts`: load or generate `{ publicKey, privateKey, subject }` at `OGM_VAPID_KEY_FILE` (default `$OGM_CONFIG_DIR/env/ogm-api.vapid.json`), mode 0600, `subject = 'mailto:' + OGM_VAPID_SUBJECT`.
- Routes under `/api/v1`: `GET /push/vapid-public-key`, `POST /push/subscriptions` (`PushSubscriptionInput`, upsert by endpoint for the user), `DELETE /push/subscriptions` (by endpoint), `GET /notifications?unread=1&limit=`, `POST /notifications/:id/read`, `GET /notifications/stream` (SSE, `Last-Event-ID`, keepalive comment every 25 s), and `POST /internal/notifications/emit` (service principal; body `NotificationTrigger`).
- `services/api/src/notify/deliver.ts`: `deliver(trigger)` → render title/body/url per kind → insert one row per `userIds[]` → fan out to open streams → `webpush.sendNotification` per subscription with `TTL 3600`, `urgency normal`; 404/410 responses delete the subscription; other failures increment `failures` and drop the subscription after 5.
- Subscribe `events.on('notify', deliver)` at mount.

## Non-goals

- The service worker, permission prompt and subscribe call in the browser (OGM-071); the in-app notification list UI (OGM-071/073).
- Emitting the triggers: `job.started` (OGM-013 scheduler), `build.done` (OGM-032 projection or OGM-045 when a build is `tested`), `intake.report` (OGM-064 through the internal route). Recipient resolution is the emitter's (`userIds`).
- Any email/SMS fallback (rejected, E01-16) or push provider (none).

## Contract and invariants

Consumer of OGM-010: copy `Notification`, `NotificationKind`, `PushSubscriptionInput`, `NotificationTrigger` from `packages/contracts/notifications.ts`; do not redefine. The T01 §4 line quoted in OGM-010 (`POST /api/v1/push/subscriptions { endpoint, keys }`; `GET /api/v1/notifications/stream` SSE `event: build.done | job.started | intake.report`) is this ticket's route contract.

Rendering (fixed strings; refreshable only through this ticket): `build.done` ok → title `Your build is ready`, body `<game title or gameId>`, url `/games/<gameId>`; `build.done` not ok → title `A build needs you`, same url; `job.started` → title `Your queued change started`, url `/games/<gameId>?chat=<jobId>`; `intake.report` → title `New assets arrived`, body `<dropId>: <status>`, url `/admin/intake`. Push payload = `{ id, kind, title, body, url }` only (minimal lock-screen content). SSE frame = `id: <notification id>\nevent: <kind>\ndata: <Notification JSON>\n\n`; on connect with `Last-Event-ID`, replay rows newer than that id for the user (ordered by `created_at`), then live. Invariants: one row per recipient per trigger; the stream never blocks delivery (fan-out is fire-and-forget per connection); the private key never leaves `vapid.ts`; the internal route requires `{ kind: 'service' }`.

## Failure, security, migration and accessibility cases

A `web-push` failure never fails the emitter (deliver catches per subscription and logs the status code only); a missing VAPID file directory is created with `mkdir -p` and 0700. Streams are capped at 5 per user (oldest closed) and 500 process-wide. The push payload holds no text beyond the fixed title and body (no chat text, no error text). The internal route is loopback-only by binding and token-gated. Timestamped migration. The browser-side 64 px targets are OGM-071's.
