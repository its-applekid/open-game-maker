## Outcome

Given 23 overrides on build 13, when build 14 is registered as `tested` with one control renamed and two removed, `GET /api/v1/games/:g/branches/:b/reapply/<build14>` returns a `ReapplyReport` saying 20 carried, 1 renamed, 2 dropped (AE2); the creator's answers to `needsChoice` and `conflicts` land as `kind: 'system'` transactions, and switching the branch to build 14 is one system transaction labelled "Switched to build 14".

## Context and evidence

Re-application is deterministic host code with a fixed classification and manifest-supplied hints (E08-4; A4 §7a steps 1–4): creates, then deletes, then property sets in stable key order; carried / renamed (`aliases`) / needs a choice (fails new validation, never clamped) / conflict (new base ≠ `baseValueAtEdit`, creator wins) / dropped (control or target removed, `retired`, or migration failed). A build may mark entries `superseded_by_job` only for controls in the request's `targetControls[]` (T06 field, passed by OGM-031). Dropped entries stay in the log; only the reduction drops them, so no archive table (E08-4). Resolved here: when the new base value deep-equals the creator's value the entry is carried and redundant (the fold in OGM-045 produces exactly this case); `migrateOverride` is a game-side function that cannot cross the JSON manifest, so V1 treats a control listed under `manifest.overrides.migrate` as `needs_choice` with the new default as `allowed`.

## Scope

- `packages/design-log/src/reapply.ts`: `reapply({ from, to, workingSet, targetControls })` → `{ report: ReapplyReport; rebased: WorkingSet; switchPatches: Patch[]; switchInverse: Patch[] }`, pure.
- `services/api/src/design/reapply.ts`: `computeReport(db, src, branchId, toBuildId)` (reduce at the current build, load both manifests and base docs, call the library, persist), `onBuildTested(buildId)` export for OGM-045 to call, `reapply_reports` table.
- `GET /api/v1/games/:g/branches/:b/reapply/:buildId` → stored report, computed on demand if absent.
- `POST /api/v1/games/:g/branches/:b/reapply/:buildId/answers` `{ answers: { key, choice: 'use_allowed' | 'keep_mine' | 'discard' | 'use_builder' }[] }` → system transactions through OGM-041's append.
- `POST /api/v1/games/:g/branches/:b/switch` `{ buildId }` → one system transaction (label "Switched to build <n>", `baseBuildId: buildId`, patches = renames and drops), sets `branches.latest_build_id`.

## Contract and invariants

Consumer: copy `ReapplyReport`, `WorkingSet`, `OverrideEntry`, `Transaction`, `Build` from OGM-040's contract files; copy `GameManifest.overrides { aliases: Record<string,string>; retired: string[] }` from OGM-020's `packages/contracts/src/game.ts`; do not redefine. Classification order and rules (fixed; tests encode each row):

| Case | Detection | Result |
|---|---|---|
| carried | control and target exist in `to`; `validateValue` passes; new base equals `baseValueAtEdit` or equals `value` | `carried` |
| renamed | `controlId` in `to.manifest.overrides.aliases` | re-key, then classify the re-keyed entry |
| needs_choice | `validateValue` fails on the new control, or control listed in `overrides.migrate` | `needsChoice {mine, allowed}`; the build's value applies until answered |
| conflict | new base value ≠ `baseValueAtEdit` and ≠ `value` | `conflicts {mine, builder}`; creator's value applies |
| superseded | `controlId` in the job's `targetControls[]` | `dropped {reason:'superseded_by_job'}`; the build's value applies |
| dropped | control missing and not aliased, or in `retired`; target entity absent in `to` base and not created by the creator | `dropped {reason:'control_removed' | 'target_removed'}` |

Invariants: the report is a pure function of `(from base doc + manifest, to base doc + manifest, workingSet, targetControls)` and is byte-stable under `canonical`; the log is never rewritten (a switch is a new transaction whose patches re-key renamed entries and remove dropped ones); answering a choice is a `system` transaction with `label` naming the control; `GET` after `POST answers` reflects the answers (recomputed).

## Failure, security, migration and accessibility cases

A build whose manifest fails schema validation yields no report and a 422 naming the build (the build stays `tested`; OGM-045's concern to mark). Answers for keys not in the report → 409. Switching to a non-`tested` build → 409. The switch and answers routes require the edit lease like any manual write (they are `system` transactions carrying the caller's `sessionId` for fencing). One timestamped migration; no secrets; no UI here (OGM-075 keeps 64 px targets on the card's buttons).
