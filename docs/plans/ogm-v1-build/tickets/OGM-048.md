## Outcome

`POST /api/v1/games/:g/fork {releaseId, visibility, name?}` creates a new game row with `forkedFrom {gameId, releaseId}`, a new repository in the creator's connected GitHub holding the release tag's tree (commit service `fork`), a `main` branch with an empty log, a first `Build` row that plays the source release's artifact, the source's achievement definitions copied with provenance, and the source's upload references re-pointed to the new game; forking a release whose lockfile holds a non-redistributable asset into a public repo is refused with the rule named; the fork holds zero saves, awards, progress or analytics rows.

## Context and evidence

A fork copies the published release pair and achievement definitions into a new game and repo and never runtime data (E08-12; spec §5.17, §9.4; A5 §4.3 "Forks"); because the fold (OGM-045) makes `design/*.json` complete at the release tag, a fork is `clone tag → new repo in the creator's GitHub (A11) → copy snapshot row and achievement defs → re-run usage-rights check` with deterministic Git ops and no reasoning agent. Paid-pack assets force private repos; forking a public game into a private one is fine, the reverse must re-check rights with T05's check (E08-12; release plan "Repos"). Forks keep their copy of uploads (decision log). Only the commit service writes to GitHub (D-COMMIT). Resolved here: provenance is two columns on `games` (`forked_from_game_id`, `forked_from_release_id`), not a new table; the fork's first build references the source artifact directory (content is immutable) until the fork's first own build; suggest-back or PRs between forks are out of V1.

## Scope

- `services/api/src/forks.ts` (a single-file context: router plus `forkGame`), mounted by the directory scan (as `forks/routes.ts` if the scan requires a directory; refresh).
- Migration adding `games.forked_from_game_id`, `games.forked_from_release_id` (nullable), plus `games.forkable` (default true) if OGM-012's row lacks it.
- `POST /api/v1/games/:g/fork {releaseId, visibility: 'public'|'private', name?}` → 201 `{ game, build, release: null }` | 403 (policy, or source `forkable: false`) | 404 (release not of this game) | 422 `{rights: [...]}` (public visibility with non-redistributable assets) | 502 `{verdict}` (commit service refused).
- Steps in order inside `forkGame`: authorize `game.fork` on the source; load the release and its build and snapshot (OGM-045); rights check via OGM-062 on the release artifact's `assets.lock.json` with the requested visibility; create the game row with provenance and the creator as owner; `ensureMainBranch(newGameId)` (OGM-041); commit `fork {sourceGameId, sourceSha: release fold sha, newGameId, owner, visibility}` → `{sha}`; insert `Build {gameId: new, branchId: main, gitSha: sha, sdkVersion, saveSchemaVersion, achievementCatalogHash: from source build, status: 'tested', artifact: 'present'}` with `artifactPath` referencing the source artifact; `copyCatalog(source, new, null)` (OGM-047); re-point upload references (OGM-005 roots list) from the source game to the new one; return.
- Transactional: the game row, build row and catalog copy are inserted in one SQLite transaction after the commit call succeeds; a commit failure leaves no rows.

## Contract and invariants

Consumer: copy `CommitOp` (`{ kind: 'fork'; sourceGameId; sourceSha; newGameId; owner }`), `CommitResult`, `BoundaryVerdict` from OGM-035's `packages/contracts/src/commit.ts`; copy `Release`, `Build`, `OverrideSnapshot`, `AchievementDef` from OGM-040's contract files; copy the lockfile shape from OGM-062's `packages/contracts/src/assets.ts`; do not redefine. Invariants: the source release must belong to `:g` and be a `publish` or `rollback` release (drafts cannot be forked); the rights check runs before any write and before the commit call; `visibility` sent to the commit service equals the requested one (the `CommitOp.fork` shape carries no visibility, so the fork is followed by `set_visibility` when the requested value differs from the commit service's default; one extra op, idempotent); the new game's `main` branch has `headRev 0` and `latestBuildId` = the new build; `forkedFrom` is immutable; zero rows in `save_*`, `achievement_awards`, `achievement_progress`, `creator_analytics_*` for the new game after a fork (test asserts counts).

```http
POST /api/v1/games/:g/fork {releaseId, visibility, name?}

  | 403 | 404 | 422 { rights: [{ assetId, rule }] } | 502 { verdict: BoundaryVerdict }
```

## Failure, security, migration and accessibility cases

Commit failure after the rights check → nothing persisted, verdict returned verbatim. Partial GitHub state (repo created, tag push failed) is the commit service's to make idempotent by `newGameId`; this ticket retries with the same `newGameId` once and then surfaces 502. The GitHub credential lives only in the commit service (D-COMMIT); the API passes the creator's connected `owner` login, never a token. Uploads are re-referenced, not duplicated (content-addressed store), so no bytes move. One timestamped migration. UI is OGM-073/OGM-077's (64 px fork button).
