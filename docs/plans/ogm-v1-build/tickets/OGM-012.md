## Outcome

`authorize(actor, action, resource)` in `packages/policy` answers the A7 matrix (minus guardian and child columns) as a test table with deny-wins precedence; the API holds families (owner, admins, members), games with their GitHub repo fields, and single-use hashed invitations of kinds `member`, `play`, `room` gated by the family allowlist switch; every route in this lane calls `authorize()` and nothing else decides.

## Context and evidence

E01-10: A7 R04's four dimensions reduce to three in V1 (`platformRole`, `capability`, `game.ownerId`); the family owner cannot be removed (spec §4.1); admins cannot edit or take over another adult's game (release plan, §6 Q5 resolves the "takeover" row to the owner's own devices only); `maintainer` is an env allow-list, never grantable in-app. E01-11: invitations are an own table (128-bit random token stored hashed, single-use, 48–72 h, bound to the recipient email, role fields server-side, per-inviter rate limit), not the Better Auth organization plugin; A2 keeps invites family-only behind an admin switch. R6 and the decision log "Repos": each creator connects their own GitHub and the platform creates one repo per game, public or private by the creator's pick, paid packs forcing private (D-COMMIT: the commit service does the GitHub write). Resolved: no accountless guests in V1 (A7); "either side takes over" applies only between one user's devices.

## Contract and invariants

Quoted from T01 §4 (producer: this ticket):
```ts
type Actor = { userId: string; platformRole: 'maintainer'|'admin'|'none'; capability: 'creator'|'player'; familyId: string };
type Action = 'game.create'|'game.edit'|'game.publish'|'game.play'|'game.fork'|'job.create'|'job.cancel'|'member.invite'|'admin.budget.set'|'report.file';
export function authorize(actor: Actor, action: Action, resource: { gameId?: string; ownerId?: string; familyId?: string; visibility?: 'listed'|'private' }): { ok: true } | { ok: false; reason: string };
```
Extension (this ticket): `Action` also accepts `'admin.members.manage' | 'admin.settings.set' | 'admin.analytics.read' | 'game.delist' | 'report.view'`; `Resource` gains `inviteKind?: 'member'|'play'|'room'` and `targetRole?: 'owner'|'admin'|'member'`.

Rules (deny wins, in this order): maintainer may do everything except act as a game owner silently (edit/publish of another's game is allowed only with `resource.audit = true`, returned as `reason: 'audited'` on ok); cross-family is always denied; `game.edit`/`game.publish`/`game.delist`-as-owner require `ownerId === userId`; admins get `admin.*`, `member.invite` of any kind, `game.delist` within the family, and never `game.edit` of another's game; creators get `game.create`, `job.create`, `job.cancel` on own games, `member.invite` with `inviteKind: 'play'|'room'` only; players get `game.play` on listed games or private ones they are explicitly granted (room invite), `report.file`, and nothing that spends; `game.play` on a `private` game needs `ownerId === userId` or an accepted `play`/`room` invitation.

Tables: `families(id, name, owner_user_id, friends_allowed INTEGER DEFAULT 0, created_at)`; `family_members(family_id, user_id, role owner|admin|member, capability creator|player, joined_at, PRIMARY KEY(family_id, user_id))`; `games(id, family_id, owner_id, title, visibility listed|private, github_owner, github_repo, repo_visibility public|private, repo_url, created_at, delisted_at)`; `github_connections(user_id PRIMARY KEY, login, installation_id, connected_at)`; `invitations(id, family_id, kind member|play|room, email, token_hash, capability, game_id, room_id, inviter_id, expires_at, accepted_at, accepted_by, revoked_at, created_at)`; `game_grants(game_id, user_id, source_invite_id, PRIMARY KEY(game_id, user_id))` (explicit play grants on private games). `RepoProvisioner { provision(game: { id; title; owner: { login; installationId }; visibility }): Promise<{ owner; repo; url }> }` with `CommitServiceRepoProvisioner` (POST `/internal/commit` `{ kind: 'create_repo', … }` per T03 §4) and `NullRepoProvisioner` for tests.

## Acceptance and verification

### Agent gate
- `pnpm --filter @ogm/policy test`: the matrix table (≥ 60 rows: every action × maintainer/admin/creator/player × own/other/other-family) passes; flipping any row's expectation fails. Fails without `authorize.ts`.
- `pnpm --filter @ogm/api test -- accounts games invites`: owner removal is 409; admin `PATCH` of another's game is 403; `POST /games` as a player is 403; a creator's game provisions through a recorded `NullRepoProvisioner` call and stores `github_owner/repo`; an invite token accepts once (second accept 410), expires at 72 h, is bound to the session email (mismatch 403), and is rate-limited at 10/day per inviter; `friends_allowed` gates non-member `play`/`room` invites; `resolveGame` returns the family and owner. Every test fails without the production change.

## Failure, security, migration and accessibility cases

Invite tokens are 128-bit from `crypto.randomBytes`, stored as SHA-256, never logged; the link carries no role claim. The accept route is idempotent on the same session and refuses a different email. `games.repo_url` is written only after the provisioner returns; a provisioner failure leaves the game row in `repo_visibility` with `repo_url NULL` and returns 502 `repo_provisioning_failed` (retry is `POST /games/:id/provision`, owner only). Cross-family access is denied before any row is loaded. Timestamped migration; no UI.
