## Outcome

A creator can `POST /api/v1/games/:g/branches {name:"Spooky monsters"}` and get a `Branch` with `forkPoint {parentBranchId, parentRev, gitSha}`; the new branch replays the parent's log to the fork point and then its own; a sixth active branch is refused (409 `cap_active`); archive keeps the row and its log; every branch reports a derived version string such as `1.3.2` where major counts publishes on `main`, minor counts tested builds since the fork and patch counts transactions since the branch's latest build.

## Context and evidence

A version is a Git branch plus a fork point `(parentBranchId, parentRev)` in the design log; `main` is a `Branch` row with `forkPoint: null` so there is one code path; cap 5 active; archive, never delete; builds, saves, rooms and analytics carry `branchId` (E08-8, A1). aiur serves one base branch per repository and repairs any PR back to it, so agent code jobs run on `main` only in V1 and branches diverge in Git only through fold and merge by the commit service (E08-9, D-BRANCH-BASE); the per-ticket base branch is filed upstream by OGM-030's lane. Kevin's 2026-10-29 counter scheme outranks A5 semver: numbers are derived from counts and never stored; `saveSchemaVersion` is the only compatibility signal (E08-7, D-VERSION). Resolved here: T03 §4's `CommitOp` has no branch-creation op, so a branch's `gitRef` is recorded as `branch/<id>` and the ref is materialised by the commit service only when the branch first needs Git (merge landing in OGM-044 via `fold_design`); nothing is pushed at creation.

## Scope

- `services/api/src/branches/{routes,service,version-counts}.ts`: `POST /api/v1/games/:g/branches {name, fromBranchId?}` (fork at the parent's head; `latestBuildId` copied from the parent; `gitSha` = parent's latest build `gitSha` or `null` when no build); `GET /api/v1/games/:g/branches` (with `version` per branch); `GET …/branches/:b`; `POST …/branches/:b/archive`; `PATCH …/branches/:b {name}`.
- Cap: 5 `active` branches per game excluding `main` (409 `cap_active` with the list); archived branches keep their log and can be read, not written (OGM-041's append rejects `status !== 'active'` through a check this ticket adds in `store.ts`'s exported guard hook).
- `packages/design-log/src/version.ts`: `deriveVersion({publishCount, buildsSinceFork, txSinceLatestBuild}) → string`.
- `VersionCounts` provider: `txSinceLatestBuild` implemented here from OGM-041's rows; `publishCount` and `buildsSinceFork` read OGM-045's tables when present (one file, two functions marked for OGM-045 to complete; they return 0 until then).
- UI copy string exported for OGM-077: "Builders work on the main version" (E08-9).

## Contract and invariants

Consumer: copy `Branch` from `packages/contracts/src/branches.ts` (OGM-040) and `CommitOp` from `packages/contracts/src/commit.ts` (OGM-035); do not redefine. This ticket's own contract:

```ts
// packages/design-log/src/version.ts
export function deriveVersion(c: { publishCount: number; buildsSinceFork: number; txSinceLatestBuild: number }): string; // `${major}.${minor}.${patch}`
// services/api/src/branches/version-counts.ts
export interface VersionCounts { publishCount(gameId): Promise<number>; buildsSinceFork(branch: Branch): Promise<number>; txSinceLatestBuild(branch: Branch): Promise<number> }
// Routes
POST /api/v1/games/:g/branches {name, fromBranchId?}  → 201 Branch | 409 {error:'cap_active', active: Branch[]} | 422
GET  /api/v1/games/:g/branches                        → { branches: (Branch & { version: string })[] }
POST /api/v1/games/:g/branches/:b/archive             → 200 Branch(status:'archived') | 409 (main cannot be archived)
```

Invariants: `main` has `forkPoint: null` and cannot be archived or renamed; a fork point is captured atomically with the parent's `head_rev` at creation (same SQLite transaction); `replay(child)` equals `replay(parent, upTo parentRev)` followed by the child's log; version numbers are computed on read, never stored; `buildsSinceFork` counts `builds` rows with `branch_id` = this branch and `status = 'tested'` created after the fork (for `main`, since the last publish); `patch` resets when `minor` rises because it counts transactions after the latest build's registration.
