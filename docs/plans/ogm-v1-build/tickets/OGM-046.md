## Outcome

A game that calls `serialize()` gets its state to the cloud: `PUT /api/v1/saves/:g/:slot` with `If-Match: <headRevision>` and `Idempotency-Key: <deviceId>:<clientSeq>` returns `{revision}`, 409 on a stale revision, 423 when another device holds the play lease, 413 above 512 KB; a retried upload with the same key is a no-op; the SDK-side machine moves `idle → pending_local → saved_local → saved_cloud | conflict | queued | read_only`; loading a slot one schema behind runs `migrate` once and keeps the original revision; a slot whose schema is newer than the restored build reads `incompatible_after_rollback`.

## Context and evidence

Saves are OCC revisions with a device lease and an IndexedDB outbox; one autosave plus three manual slots; migration is lazy, one step, from the predecessor release only; rollback marks and deletes nothing (E08-11; A5 §3.2–3.7; spec §5.16). Two independent guards (lease and revision) are the design because a stale tab is the only place progress can be destroyed. A draft save on a branch has no release, so revisions record `branchId`, `buildId`, `releaseId?` (E08-11). The game iframe is cross-site to the app and holds no cookies (D-GAMES-ORIGIN), so the game only emits `save.write` over the bridge and the host app performs the upload. Resolved here: compatibility status is computed from the schema numbers the loading client supplies (`?schema=N&migratesFrom=M`), so this ticket depends on no releases table; the `fetch keepalive` 64 KB limit is treated as real (outbox first, upload later when the body exceeds 60 KB).

## Scope

- Tables (timestamped migration): `save_slots` (PK `user_id, game_id, slot_id`), `save_revisions` (PK `user_id, game_id, slot_id, revision`; unique `(user_id, game_id, slot_id, device_id, client_seq)`), `play_leases` (PK `user_id, game_id`).
- Routes: `GET /api/v1/saves/:g` (slots with status for `?schema&migratesFrom`); `GET /api/v1/saves/:g/:slot[?revision=]` (payload stream + headers); `PUT /api/v1/saves/:g/:slot` (octet-stream gzip JSON, `If-Match`, `Idempotency-Key`, `X-Save-Schema`, `X-Save-Branch`, `X-Save-Build`, `X-Save-Release?`, `X-Save-Reason`, `X-Save-Label?`) → 200 `{revision}` | 409 `{headRevision}` | 423 `{heldBy}` | 413 | 422; `POST /api/v1/saves/:g/lease {deviceId, tabId, takeover?}` → `{expiresAt}` | 409 `{heldBy: deviceId}`; `POST …/lease/heartbeat`.
- Retention: last K = 5 revisions per slot plus every revision referenced by `migrated_from_revision`.
- `packages/sdk/src/saves/machine.ts` (iframe side: dirty tracking, triggers pause / declared checkpoint / `visibilitychange` / 30 s interval, `canSaveNow()`, emits `save.write`); `packages/sdk/src/saves/outbox.ts` + `client.ts` (host side, `idb` 8: queue, retry on `online` and launch, If-Match/Idempotency-Key, conflict keep-both as a local "Copy from <device>" entry, `read_only` on 423).
- Migration at load (`client.ts`): schema == current → restore; == `migratesFrom` → `migrate` via bridge, upload as `reason:'migration'` with `migratedFromRevision`; otherwise `unsupported_old`; head schema > current → `incompatible_after_rollback` with the list of older matching revisions.
- `countSavesAboveSchema(gameId, schema)` exported for OGM-045's rollback confirm; one-line wiring in `services/api/src/releases/rollback.ts`.

## Contract and invariants

Consumer: copy `SaveSlot`, `SaveRevision`, `PlayLease` from OGM-040's `packages/contracts/src/saves.ts`; copy `save.write` / `save.restore` envelopes and `GameInstance.migrate` from OGM-020's `packages/contracts/src/{bridge,game}.ts`; do not redefine. Invariants: a `PUT` succeeds only when `If-Match` equals the slot's `headRevision` (new slot: `If-Match: 0`) and the caller's `deviceId` holds the play lease; the same `Idempotency-Key` returns the original `{revision}` without a new row; payload ≤ 512 KB after gzip, opaque to the server (only envelope, size, auth and schema number validated); revisions are never updated; `status` is derived at read time from `(headSchema, ?schema, ?migratesFrom)`: equal → `ok`; `headSchema === migratesFrom` → `needs_migration`; `headSchema > schema` → `incompatible_after_rollback`; else `unsupported_old`; a conflict never auto-picks a winner (the client keeps both).

```http
PUT  /api/v1/saves/:g/:slot   If-Match: 7  Idempotency-Key: dev_a:42  X-Save-Schema: 3 …  body: gzip JSON  → 200 {revision: 8} | 409 {headRevision} | 423 {heldBy} | 413
GET  /api/v1/saves/:g?schema=3&migratesFrom=2                                                   → {slots: SaveSlot[]}
POST /api/v1/saves/:g/lease {deviceId, tabId, takeover: false}                                   → 200 {expiresAt} | 409 {heldBy}
```

## Failure, security, migration and accessibility cases

A dead tab's lease expires after 30 s of missed heartbeats; its queued upload then fails 423 and stays local for the player to copy. Payloads are stored as opaque BLOBs; no field is parsed server-side, so no prompt text or PII handling applies beyond the account scope (a user reads only their own saves; `authorize(actor,'game.play')` for the game). The job token and service token are not used here. One timestamped migration. The games iframe never calls these routes directly (cross-site, no cookies); only the host app does. UI is OGM-075's (64 px slot targets).
