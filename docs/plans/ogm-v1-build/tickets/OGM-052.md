## Outcome

An owner calls `POST /api/games/:gameId/rooms` and gets a `roomId` and grant; `POST /api/rooms/:roomId/invites` returns a link; a signed-in, age-screened, allowlisted friend opening `/join/<token>` in the app lands on the game route holding a grant, pin and rooms URL; revoke and the rooms service's ended callback are recorded; every path is covered by API tests and a route test.

## Context and evidence

E07-7 replaces A7's anonymous guest codes: every joiner is a signed-in adult; the room needs one thing, a grant binding `{userId, roomId, role, exp}`. E01-11: invitations are one own table with hashed single-use tokens and kinds `member | play | room` (OGM-012 builds the table and the family allowlist switch, A2). E01-9: invitees pass the age screen; E01-10: `authorize()` is the one policy call. E11-6: the socket cannot use the cookie, so the API mints a short-lived grant and the client connects directly to `wss://…:8443/ws/rooms`. Resolved, do not reopen: R4 (single-use token) outranks E07-7's "capability link" default, so one invite link admits one friend and the owner taps Invite once per friend; re-entry after a grant expires is a self-service re-grant for admitted members, not a reusable link. Rooms are created through OGM-051's loopback internal API; the API stores the room row.

## Scope

- `services/api/src/rooms/`: `routes.ts` (directory-scanned mount) with
  `POST /api/games/:gameId/rooms {branchId, buildId, maxPlayers?} → {roomId, grant, pin, roomsUrl}` (owner only; calls `POST /internal/rooms` on the rooms service; inserts `rooms` row; maxPlayers from the game setting, clamp 1..8),
  `POST /api/rooms/:roomId/invites {email?} → {url}` (owner only; `createInvitation({kind:'room', roomId, gameId, email?, expiresAt: +7 d})` from OGM-012; `url = <app origin>/join/<token>`),
  `GET /api/join/:inviteToken → {roomId, grant, pin, roomsUrl}` (session required; age cookie/attestation required; `authorize(actor,'game.play',…)` plus family allowlist; consumes the token on first use, idempotent for the same user; inserts `room_members`; signs a player grant),
  `GET /api/rooms/:roomId/grant → {grant, pin, roomsUrl}` (owner or admitted member; re-mint after expiry),
  `POST /api/rooms/:roomId/revoke {jti?|userId?} → 204` (owner only; forwards to the rooms internal revoke; marks the member revoked),
  `POST /internal/rooms/:roomId/ended {reason, endedAt} → 204` (bearer `OGM_ROOMS_INTERNAL_SECRET`; writes `endedAt`, `endReason`).
- `services/api/src/rooms/schema.ts` and a timestamped migration: `rooms (id, gameId, branchId, buildId, ownerId, maxPlayers, createdAt, endedAt, endReason)`, `room_members (roomId, userId, invitationId, joinedAt, revokedAt)`.
- `apps/web/src/routes/join/route.tsx`: reads `:inviteToken`; not signed in → `/age` then `/signin?next=/join/<token>`; signed in → `GET /api/join/:token`; success → store `{roomId, grant, pin, roomsUrl, expiresAt}` in `apps/web/src/routes/join/grant-store.ts` (memory only) and navigate to `/g/:gameId?v=<branchId>&room=<roomId>`; failure states render one line each (expired, used, not allowed, room ended).

## Contract and invariants

Consumer of the room protocol: copy `RoomGrant`, `RoomPin` and `signGrant` from OGM-050; do not redefine. Consumer of OGM-051's loopback API: `POST /internal/rooms`, `POST /internal/rooms/:roomId/revoke` (quoted in OGM-051.md). Routes this ticket owns, verbatim from T07 §4.2 with the two additions marked:

```
POST /api/games/:gameId/rooms            {branchId, buildId, maxPlayers?}  → {roomId, grant}       owner only; creates the room via the rooms service internal API
POST /api/rooms/:roomId/invites          {}                                 → {url}                 url = https://app.<host>/join/<inviteToken>, 7-day expiry, revocable
GET  /api/join/:inviteToken               (signed-in, age-screened, allowlisted) → {roomId, grant, pin, roomsUrl}
POST /api/rooms/:roomId/revoke           {jti | userId}                     → 204                   pushes to the room's revocation list
POST /internal/rooms/:roomId/ended       {reason, endedAt}   (rooms → api, shared secret)           records the session; triggers nothing else in V1
GET  /api/rooms/:roomId/grant            (owner or admitted member)         → {grant, pin, roomsUrl}   [added: re-grant after the 10-min expiry]
```
`POST …/rooms` also returns `pin` and `roomsUrl` (same shape as join) so the host needs one call. Invariants: a grant is minted only for the signed-in user (`sub` = session user, `name` = display name, never email), `ttlSec ≤ 600`; `roomsUrl = ${OGM_PUBLIC_ORIGIN}/ws/rooms`; an invite token is single-use (`consumeInvitation` marks `acceptedBy`; a second `GET` by the same user re-mints, by another user fails `410`); `email`, when given at creation, must match the consumer's email; the room row is the source for `ownerId` passed to the rooms service; `ended` is idempotent.

## Failure, security, migration and accessibility cases

Grants and invite tokens never appear in logs, analytics or URLs other than the invite path itself; the raw invite token is shown once to the owner. Enumeration: `GET /api/join/:token` answers 410 for unknown and used tokens alike, rate-limited per IP by OGM-011's limiter. The rooms service down → 503, no row written. Migration is one timestamped file adding two tables; no data backfill. The join route's visible controls (sign-in continuation) are 64 px primary targets; error lines carry `role="status"`.
