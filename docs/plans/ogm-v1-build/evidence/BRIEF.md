## Output format

Markdown, 150–400 lines, with these sections in this order:

1. **Scope of this track** (3 lines).
2. **Evidence packets.** One per claim, in this exact shape:
   ```
   ### E<track>-<n>: <claim in one line>
   - Claim / current behavior:
   - Source and exact locus: (file path and line or section; aiur module path when it's aiur)
   - Why it matters:
   - Confidence and freshness: [M]/[V]/[I]/[O], as of commit
   - Contradiction or open question:
   - Suggested requirement/decision impact:
   ```
   Aim for 10–25 packets. Include the ones that contradict the research or the architecture doc.
3. **Existing owners and reuse targets.** A table: capability → what exists today (file paths, language, tests present yes/no) → keep / port to TypeScript / replace → why.
4. **Interfaces and contracts this track defines or consumes.** For each: owner (this track or another), one concrete sketch (a JSON message, a TypeScript type, a CLI signature, or a route). Keep sketches short and real.
5. **Candidate tickets.** 4–10 rows: working title, one-line outcome, code surface it would write (packages/directories/files), complexity 1–5 (1 localized known pattern; 2 one subsystem; 3 one bounded context with a new contract; 4 cross-context; 5 irreducible), hard prerequisites (which other candidate or track's contract), what it must not absorb.
6. **Risks and unknowns** needing a decision or a spike, each with a recommended default.
7. **Self-hosting notes**: anything in your area that changes because it runs on this machine rather than Railway/E2B, with what you checked on the host (read-only commands such as `which`, `--version`, `systemctl --user status` are fine).

Write for a planner who will merge twelve of these: be concrete, cite paths, keep opinions marked. Do not restate the research; extract what decides tickets.
