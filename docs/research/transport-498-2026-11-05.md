## 1. Outcome

1. **Build the seam N1 already specified, and nothing larger.** `apps/web/src/net/transport/` gets the `Transport`
   interface of §6.2 plus the `seat` field a per-pair switchboard needs, a `WsRelayTransport` that wraps today's room client, a `WebRtcTransport` on native
   `RTCPeerConnection`, and a per-pair selector. The game iframe, the bridge envelopes and the room protocol do not
   change: the seam sits in the host app under `bridge-forwarding.ts`.
2. **The relay stays the default and the fallback.** WebRTC is attempted per pair, only after 5 s of measured baseline
   and only when that baseline is bad. No pair is promoted silently; a switch is a diagnostic the other seats can see.
3. **Measure first, and measure the right thing.** The measurement says the current path's *headline* latency is not
   network latency: a peer watches its own input land ~128 ms late on a perfect LAN and ~176 ms late across a 100 ms
   round trip. 100 ms of that is `interpolationDelayMs`, ~20 ms the 20 Hz snapshot cadence, and the rest is the round
   trip. **N2's per-seat authority removes the first two without any transport work**; N4's honest claim is one fewer
   WAN leg per direction, a bounded tail under loss, and no host-upstream fan-out — not a lower input latency.
   §3 has the numbers.
4. **WebRTC carries inputs and state; events stay on the relay.** The event channel is reliable and ordered per sender
   already, the room is a guaranteed path, and a reliable data channel has the same head-of-line behaviour as the TCP
   underneath it (§3.3 measured exactly that). Keeping events on the relay means one authority for rules-relevant
   messages and no dual-receive dedupe in N4.
5. **STUN now, TURN only if the operator chooses to run it.** Host candidates plus a public STUN resolver cost nothing
   and cover LAN and any pair that can hole-punch. Symmetric NAT needs a TURN relay, and the only zero-cost TURN is
   self-hosted `coturn` on the operator's node with one UDP port — which this deployment cannot expose today, because
   Tailscale Funnel is HTTP(S)-only (`docs/ops/ingress.md`). §8 has the option table, costs and the exact credentials an
   operator would create. **Nothing is bought or provisioned here.**
6. **No new dependency.** Native `RTCPeerConnection` + `RTCDataChannel`; the stats estimator, selector and link
   simulator are local TypeScript. This keeps rule "pin exact versions" untouched and keeps the transport testable
   without a browser (fake peer connection injected, as §7 specifies).

## 2. What the current path is (verified in source)

### 2.1 The wire

```
peer browser ─┐                          ┌─► 127.0.0.1:$OGM_ROOMS_PORT (Colyseus, relay only)
              ├─ wss://<tailnet-host>:8443/ws/rooms/*  (Tailscale Funnel)
host browser ─┘                          └─► the same room, one message hop apart
```

- Every room socket is `wss://<tailnet-host>:8443/ws/rooms/*`, served by Tailscale Funnel and proxied to
  `127.0.0.1` (`docs/ops/ingress.md`, origin map). Netlify carries no WebSocket upgrades, so it is never on the socket
  path (`docs/ops/netlify-proxy.md`, "Sockets"). Netlify is on the path only for the static app and `/api/*` rewrites.
- `PROTOCOL_VERSION = 1` and the room is relay-only: `services/rooms/src/game-room.ts` validates each message against
  `packages/contracts/src/room.ts` and forwards it — `snapshot`/`event` are broadcast from the editor to everyone else,
  `input` goes to the editor session only.
- The game iframe never holds the socket: `apps/web/src/net/bridge-forwarding.ts` maps room messages to bridge
  envelopes (`net.input`, `net.snapshot`, `net.event`, `net.players`, `net.role`, `phase`) and re-checks each payload's
  size cap before it crosses.
- Cadences today: a peer sends one `net.input` per fixed step (60/s, `packages/sdk/src/net/peer.ts` `sendFrames`), the
  host answers with a snapshot every third tick (20 Hz, `packages/sdk/src/net/host.ts` `afterStep`), and a peer renders
  100 ms behind the newest buffered snapshot with three snapshots buffered
  (`packages/sdk/src/net/index.ts:25-26`, `peer.ts` `receiveSnapshot`/`render`).
- RTT: `apps/web/src/net/room-client.ts:321` pings every 5 s and stores `Date.now() - c` on the pong. That is the only
  path-quality number the client has today, and it is coarse: one sample per 5 s, no jitter, no loss.

### 2.2 The three channels exist only in the SDK, not on the wire

`docs/plans/netcode-platform.md` §6.1 defines `input` (unreliable, unordered), `state` (unreliable, drop-oldest) and
`event` (reliable, ordered per sender). On the wire today all three are Colyseus JSON messages over one ordered, reliable
WebSocket. The reliability distinction the design needs does not exist yet [V] — which is exactly what makes the
WebRTC comparison in §3 non-trivial: the relay cannot *choose* to drop a late input, it can only be slow.

### 2.3 Neighbours whose contracts this work consumes

| Neighbour | What N4 needs from it | State on `main` |
| --- | --- | --- |
| #496 (N2) | `net.inputs` batches, `net.state`, `net.checksum`, `net.recovery*`, the per-seat controller that calls `transport.send('input', …)` | not merged; N1 §4 designs it |

N4 therefore has to be mergeable **before** N3 and still correct after it (§4.5).

## 3. Measurements

### 3.1 Method

`scripts/net/transport-bench.mjs` (dependency-free, Node 22+):

- `--wire` is arithmetic over the repository's own constants and schema shapes (§2.1) — payload bytes, RFC 6455 framing,
  and per-second totals for 2 and 4 seats.
- `--relay` **measures**. It starts a WebSocket hub in the room's role, connects a peer and a host, and runs both sides
  with the runtime's real constants: peer sends one input per fixed 16.7 ms step, host applies at its next step and
  snapshots every third tick, peer renders 100 ms behind the newest buffered snapshot. A TCP proxy on the peer's leg
  adds a fixed one-way delay, and a seeded share of chunks is held for 200 ms, which is what a TCP retransmit looks like
  to the reader. Client-side terms are therefore *reproduced*, not injected; the transport terms are *measured*.
- `--select` runs §6.5's policy as a state machine over scripted stats and prints the expected decision (§7).

Commands and their output are in the PR body. `BENCH_SECONDS` sets the length of each row (default 6 s).

What the harness is not: it is not the SDK. It does not run `GmNet`, the game loop or Colyseus; it reproduces the cadence
and the message shapes. The numbers below are the transport and pipeline, not a game's feel.

### 3.2 Wire cost [M]

Input frame, per send (the peer's own step, 60/s):

| segment | bytes |
| --- | --- |
| bridge envelope, iframe → host app | 100 |
| room client message, host app → room | 63 |
| room message after the seat stamp, room → host | 95 |
| WebSocket text frame carrying it (masked) | 101 |

Snapshot, per send (20/s):

| world | JSON state | room message | bridge message |
| --- | --- | --- | --- |
| 2 seats, 2 × 10 × 20 board + 2 avatars | 1 083 B | 1 491 B | 1 529 B |
| 4 seats, 4 × 10 × 20 board + 4 avatars | 2 123 B | 2 879 B | 2 917 B |
| contract ceiling (65 536 B before base64) | 65 536 B | 87 424 B | 87 480 B |

Per second through the relay, both directions, application bytes plus framing:

| seats | peer → room input | room → host input | host → room snapshots | room → peers snapshots | total |
| --- | --- | --- | --- | --- | --- |
| 2 | 4.0 KiB/s | 5.7 KiB/s | 29.3 KiB/s | 29.2 KiB/s | **68.2 KiB/s** |
| 4 | 12.1 KiB/s | 17.1 KiB/s | 56.4 KiB/s | 168.9 KiB/s | **254.5 KiB/s** |

Three things to take from that table:

- The design's §13 estimate ("4 seats × ~30 input packets/s × ~350 B ≈ 42 KB/s") counts inputs only. At four seats the
  relay carries **6× that**, and **66 % of it is the host's snapshot fan-out** (one 2.9 KiB message × 3 peers × 20 Hz).
- Fan-out is the part a mesh removes: on WebRTC the same snapshot leaves each seat once per peer over that peer's own
  path instead of three times through the host's uplink. That matters on a home connection where the host is on a
  residential upstream [I].
- Base64 is a 33 % expansion before any envelope: 1 083 B of raw state becomes 1 444 base64 characters; the room
  message wraps that in 47 B and the bridge envelope adds 38 B more. That is a known, accepted cost of the JSON
  bridge and N4 must not change it; it is why a snapshot at the contract ceiling is 87 KiB on the wire.

### 3.3 Latency [M]

Measured with `--relay` on this host, `BENCH_SECONDS=8`. "input → remote display" is key press on the peer until the
host's step renders it; "own input → own display" is the same key press until the peer's own screen shows the result
(the relay path's worst case, because a peer renders the host's snapshots and simulates nothing).

| one-way delay | loss | input → remote display p50 / p95 / max | own input → own display p50 / p95 / max | event p50 / p95 / max |
| --- | --- | --- | --- | --- |
| 0 ms (loopback) | 0 % | 19 / 27 / 36 ms | 128 / 141 / 145 ms | 1 / 1 / 7 ms |
| 12 ms (24 ms RTT) | 0 % | 20 / 40 / 49 ms | 135 / 153 / 160 ms | 16 / 24 / 32 ms |
| 25 ms (50 ms RTT) | 0 % | 37 / 47 / 63 ms | 147 / 161 / 169 ms | 27 / 33 / 43 ms |
| 50 ms (100 ms RTT) | 0 % | 64 / 78 / 103 ms | 176 / 196 / 204 ms | 52 / 61 / 69 ms |
| 25 ms (50 ms RTT) | 2 % | 35 / 43 / 64 ms | 142 / 159 / 184 ms | 27 / 33 / 227 ms |
| 25 ms (50 ms RTT) | 10 % | 35 / 46 / 245 ms | 146 / 159 / 192 ms | 27 / 227 / 231 ms |

Reading it:

- **The relay's own transport cost is about one millisecond.** At loopback the input reaches the host in 19 ms, which is
  one 16.7 ms step plus the socket. Nothing in the platform's plumbing is slow.
- **Each one-way WAN leg costs its delay, and there are two of them per direction on the relay path.** Going from 0 to
  50 ms one-way adds 45 ms to input → remote display: peer → room → host. A direct data channel has one leg, so a pair
  promoted to WebRTC saves one one-way delay per direction over the relay [M from the delta, I for the direct case,
  which this harness cannot measure without a browser].
- **The interpolation delay dominates what a player feels.** 128 ms of the loopback number is client-side: 100 ms
  interpolation + ~20 ms snapshot cadence + one step. At 100 ms RTT it is 176 ms. Compare #495's target in §8.1:
  `localResponseMs ≤ 16.7 ms` and `remoteUpdateMs ≤ 100 ms p95`. **The relay path misses both today** — and a transport
  swap cannot fix either, because those ~120 ms are the *host-authoritative* design, not the network. N2's per-seat mode is
  what brings the peer's own input back to one step; N4 only removes network legs. That ordering matters for the ticket:
  #498 must not be sold as the fix for input latency.
- **A tail under loss is real and is not the input channel's to fix.** At 2 % chunk loss a single stall turns a 33 ms
  event-delivery p95 into a 227 ms maximum, and at 10 % the p95 itself is 227 ms: every message queued behind the
  stalled TCP segment waits with it. This is the concrete argument for `RTCDataChannel` with `maxRetransmits: 0` on inputs (§4.2): a late input is
  worthless, and on the relay it also delays the snapshot behind it.

### 3.4 What was not measured here

Not computable in this workspace, and therefore left to the implementation's acceptance run and the post-deploy list in
the PR:

- **Real devices and real distances.** #498 asks for two and four devices at home and across the internet. This
  workspace has one machine, no second display device and no route out to another host [M: the bench binds `127.0.0.1`].
- **The Funnel hop, and Netlify's absence from it.** Funnel *is* on the socket path (one TLS terminator and one reverse
  proxy to `127.0.0.1`) and is not reachable from here; Netlify is only on the app and `/api/*` path, so a socket
  measurement never crosses it. Its cost is expected to be sub-millisecond for queueing plus the internet RTT [I] and
  must be measured on the host with two devices.
- **A real ICE negotiation.** Native `RTCPeerConnection` in a browser is what N4 must measure; Node has no WebRTC data
  channel here. The selector's numbers can be exercised with injected stats (§7); the first honest promotion number has
  to come from a Chromium run.
- **Safari/iOS behaviour.** Untested. ICE, mDNS candidate obfuscation and data-channel throughput all differ from
  Chromium [I]. This is why the relay stays a fallback rather than a bootstrap.

## 4. Design

### 4.1 Where the seam sits

```
game iframe ──bridge──► apps/web/src/net/bridge-forwarding.ts ──► apps/web/src/net/transport/
                                                                      ├── ws-relay.ts  (today's RoomClient)
                                                                      ├── webrtc.ts    (one per promoted pair)
                                                                      └── select.ts    (per-pair policy)
```

- The transport sits **below** `bridge-forwarding.ts`, so the bridge envelopes and the game SDK never learn which
  transport is in use. N5 and N6 therefore do not depend on a transport decision, and a demotion is invisible to the
  game.
- `WsRelayTransport` is a thin adapter over `RoomClient` (`send(ClientMessage)` + `subscribe(ServerMessage)`): `input`
  → room `input`, `state` → room `snapshot`, `event` → room `event`. It also owns the timing observations §4.4 needs,
  because those come from room messages (`pong`, snapshot `seq`, input `seq`).
- `WebRtcTransport` is one object per peer pair, created only while a promotion is being attempted. It owns its
  `RTCPeerConnection`, its `ogm-input` data channel and its `getStats()` poller.
- A `TransportSwitchboard` (one per room) owns the pairs, routes `send()` per channel (local seat's own traffic never
  leaves the browser; remote traffic goes to the promoted path for that seat or to the relay), and is the only place
  that decides.

### 4.2 Channels on each transport

| Channel | `ws-relay` mapping | `webrtc` mapping |
| --- | --- | --- |
| `input` | room `input` (relayed to the host only) | `RTCDataChannel` `ogm-input`, `{ ordered: false, maxRetransmits: 0 }` |
| `state` | room `snapshot` (broadcast from the host) | the same `ogm-input` channel, 1 leading byte tag `0x02` so a reader can drop-oldest |
| `event` | room `event` (broadcast) | **stays on the relay** (§1.4) |

- One channel carries `input` and `state` because both are "latest wins" and neither may head-of-line block the other's
  *sending*; the leading tag byte is all a reader needs to route and to drop an old state.
- The event channel is not opened on the pair at all in the first version. If a later ticket moves events onto the
  pair, it must keep the relay copy until the data channel has been healthy for a full epoch, or a rules-relevant
  message can be lost in the promotion window. Recording that here keeps N4 from shipping a half-reliable event path.
- `RTCPeerConnection` is configured with `iceServers: [{ urls: <STUN list> }]` and nothing else by default (§8).

### 4.3 Selection

Per pair, with the state machine N1 §6.5 describes, tightened at two points:

1. **Probe before attempting.** The first 5 s of an epoch are relay-only for the pair, so the comparison has a baseline.
2. **One attempt per epoch per pair.** A failed attempt (`iceConnectionState` → `failed`, or still not `connected` when
   `attemptTimeoutMs = 5000` passes) marks the pair `relay-for-epoch`; it is retried on the next epoch, not in a loop.
3. **Demote on evidence, not on a single sample.** Close, event failure, or a 5 s window whose p50 RTT is above 2× the
   relay's. A promoted pair at 0.8× the relay's RTT stays promoted (hysteresis), because flapping costs more than the
   delta it removes.
4. **Announce.** Every transition posts `net.transport { epoch, seat, kind }` through the room (N3's contract) so the
   other seats and N6's overlay can see it.

Constants, with the measured baseline behind each:

| constant | value | why |
| --- | --- | --- |
| `probeMs` | 5 000 | ~300 input frames and 100 snapshots, enough for a p50 on a home link |
| `rttThresholdMs` | 80 | above this, one relay leg is most of a 60 Hz frame budget (§3.3: +1 leg ≈ +delay in input → remote display) |
| `lossThresholdPct` | 2 | measured tail: at 2 % chunk loss a stalled segment already costs ~194 ms of extra delivery (§3.3) |
| `promoteGainPct` | 30 | a promotion must remove at least a third of the path or it is not worth a switch |
| `demoteFactor` / `demoteWindowMs` | 2× / 5 000 | a slow pair has to be slower *for a while* before it is demoted |
| `attemptTimeoutMs` | 5 000 | ICE gathering + connect on a home link; a slower attempt is not worth holding a slot |

### 4.4 Stats

Every field of §6.2's `TransportStats` needs a source per pair. They are:

| field | on `ws-relay` | on `webrtc` |
| --- | --- | --- |
| `rttMs` | `ping`/`pong`, min-RTT filter over a 10-sample ring; ping cadence 1 Hz while `phase === 'playing'` (the room caps `ping` at 10/s) | `getStats()`: `candidate-pair.currentRoundTripTime` of the nominated pair |
| `jitterMs` | mean absolute successive difference of RTT samples over the same 10-sample ring | `remote-inbound-rtp.jitter` when present, else the same estimator over `currentRoundTripTime` samples |
| `lossPct` | gap count over a 5 s window over the expected sequence: snapshot `seq` on the host→peer side, `net.inputs.firstTick` on the peer→host side (N2's batches make this exact) | `inbound-rtp`/`outbound-rtp` packet counters from `getStats()` |
| `bytesOut`/`bytesIn`/`drops` | summed frame sizes the transport is given, plus `drops` counted when a send is refused by a cap | the same, plus `dropped` samples from the data channel's buffered-amount high-water mark |

The relay's `lossPct` is an estimate from sequence gaps, not from the socket: WebSocket does not report drops. It is
correct in the only sense that matters for selection — it sees a lost message — and it is the same estimator N6 needs,
so it lives in the transport, not in the overlay.

### 4.5 Signalling and the N3 dependency

WebRTC needs to exchange an SDP offer/answer and trickled ICE between two seats. The room is the only channel both
seats share, and N3 adds exactly the message for it: `net.signal { epoch, to, data }`, opaque, routed by seat, 20/s and
4 KiB per message (N1 §9.2).

- **N4 ships before N3.** It feature-detects: the switchboard attempts a promotion only when the joined room's state
  reports `protocol >= 2` (N3's v2 room) *and* a signalling sink is attached. Against a v1 room — which is every room on
  `main` today, since `PROTOCOL_VERSION` is still 1 — the switchboard is never constructed and the client's message flow
  is exactly what it is now. That is the compatibility requirement §11.3 puts on
  every v2 feature, and it keeps N4 mergeable in any order.
- **N4 does not invent a second signalling path.** No polling endpoint, no API route, no new public port.
- ICE candidates are trickled one per `net.signal` message. With two candidates per side on a home LAN, four signalling
  messages complete a pair; the 4 KiB cap holds a data-channel-only SDP of roughly 1.5 KiB with room to spare [I — a
  typical Chromium offer; the implementing ticket must log the real size once].

### 4.6 What does not change

- No file in `packages/contracts`, no bridge envelope, no `PROTOCOL_VERSION` change in N4 (N3 owns the v2 messages).
- No game code: `GmNet`, `HostChannel`, `PeerChannel` and the runtime's step are untouched; the transport is below the
  bridge.
- No published-build surface: the transport is a runtime path, not chrome. There is no flag, no overlay and no copy
  change on any screen — the design rule of `docs/plans/netcode-platform.md` §8.2 stands.

## 5. Interfaces

```ts
// apps/web/src/net/transport/types.ts
export type ChannelName = 'input' | 'state' | 'event';
export type TransportKind = 'ws-relay' | 'webrtc';

export interface TransportStats {
  readonly kind: TransportKind;
  readonly rttMs: number;
  readonly jitterMs: number;
  readonly lossPct: number;
  readonly bytesOut: number;
  readonly bytesIn: number;
  readonly drops: number;
  readonly connectedMs: number;
}

export interface TransportHandlers {
  /** `seat` is the sending seat; a transport never invents one. */
  message(channel: ChannelName, seat: number, bytes: Uint8Array): void;
  stats(stats: TransportStats): void;
  closed(reason: string): void;
}

export interface Transport {
  readonly kind: TransportKind;
  /** The remote seat this transport talks to; the switchboard keys pairs by it. */
  readonly seat: number;
  open(handlers: TransportHandlers): Promise<void>;
  send(channel: ChannelName, bytes: Uint8Array): void;
  stats(): TransportStats;
  close(reason: string): void;
}

export const TRANSPORT_LIMITS = {
  probeMs: 5_000,
  rttThresholdMs: 80,
  lossThresholdPct: 2,
  promoteGainPct: 30,
  demoteFactor: 2,
  demoteWindowMs: 5_000,
  attemptTimeoutMs: 5_000,
  statsEveryMs: 1_000,
} as const;
```

```ts
// apps/web/src/net/transport/select.ts — pure, no timers, no browser globals
export type PairState = 'ws-relay' | 'attempting' | 'webrtc';
export type Decision = 'stay-ws-relay' | 'attempt-webrtc' | 'promote' | 'stay-webrtc' | 'demote';

export function decide(input: {
  state: PairState;
  elapsedMs: number;
  relay: TransportStats;
  candidate?: TransportStats;
  candidateConnectedMs?: number;
  eventsOk: boolean;
}): Decision;
```

```ts
// apps/web/src/net/transport/index.ts
export interface TransportSwitchboard {
  /** `to` names the remote seat the bytes are for; `undefined` broadcasts them through the relay. */
  send(channel: ChannelName, bytes: Uint8Array, to?: number): void;
  /** One entry per remote seat, live. */
  stats(): ReadonlyMap<number, TransportStats>;
  /** Prompt a decision now; the switchboard also ticks on its own `statsEveryMs`. */
  evaluate(): void;
  close(reason: string): void;
}

export function createSwitchboard(options: {
  relay: Transport;
  localSeat: number;
  peers: readonly number[];
  signal?: SignalSink;          // N3's net.signal, absent on a v1 room
  createCandidate?: (seat: number) => Transport; // injected in tests; defaults to WebRtcTransport
  now?: () => number;
}): TransportSwitchboard;
```

`WsRelayTransport` implements `Transport` over `RoomClient`: `open()` subscribes, `send()` maps the channel to a room
message, and `stats()` returns the §4.4 estimates. `WebRtcTransport` implements `Transport` for one peer: `open()`
creates the `RTCPeerConnection`, the offerer side adds `ogm-input`, the answerer accepts it, and `open()` resolves on
`connectionState === 'connected'`.

## 8. STUN/TURN recommendation

**Decision: ship with no STUN/TURN server at all in the first version, then add public STUN as the default once a
browser run proves a direct path; do not adopt TURN until a real measurement shows a pair that cannot connect without
it.** Nothing is bought or provisioned by N4.

Why that order: no pair has been attempted on this platform yet, so the first thing to prove is the seam. Host
candidates alone connect on one LAN [I]. A public STUN resolver costs nothing and turns "works on the LAN" into "works
when the NATs are friendly", which covers a large share of home pairs. TURN only matters for symmetric NAT, double NAT and some mobile carriers — real problems that the
zero-cost deployment cannot serve today, because TURN needs a public UDP port and the ingress is Tailscale Funnel on
HTTPS (8443 and 10000 only, `docs/ops/ingress.md`). A silent "WebRTC is worse on your network" would be the worst
outcome, so the relay is the elective fallback and TURN is an operator decision with a cost.

| Option | Cost | Credentials / setup | Verdict |
| --- | --- | --- | --- |
| Host candidates only | $0 | none | **Phase 0.** Proves the seam; LAN and same-machine only. |
| Public STUN (e.g. a free public resolver) | $0 | none; one URL constant | **Phase 1 default** once a Chromium run connects. No relay; still fails behind symmetric NAT. |
| Self-hosted `coturn` on the operator's node | $0 in money; one public UDP+TCP port (3478) and a UDP range (49152–65535) opened outside Funnel | a `turn` user and a shared secret in `~/.config/ogm/env/rooms.env` (mode 0600), read by a small API route that mints short-lived TURN credentials (the standard `username = timestamp`, `password = HMAC-SHA1(secret, username)` scheme) | **Phase 2, operator-only.** Needs the operator to expose UDP, which Funnel cannot; the design's own risk table calls this an operator deployment decision. |
| Managed TURN from a provider | per-GB, paid, and the tier varies by provider and region | an API key in `~/.config/ogm/env/`, plus a quota to watch | **Not authorised.** Spending needs the operator. The implementation must keep it possible by making the ICE server list configurable, not by shipping a key. |

Exact costs for a managed TURN are provider- and region-specific and this workspace has no way to verify them at
purchase time; **this document therefore names no number it could not check.** If the operator wants the managed route
later, the ticket that adopts it must record the provider, the current list price for TURN relayed bytes and the
monthly minimum, and it must be an explicit spend decision.

Credentials an operator would create for the self-hosted option — the only concrete values this ticket fixes:

```ini
# ~/.config/ogm/env/rooms.env, mode 0600 (never committed, never logged)
OGM_TURN_SECRET=<at least 32 random bytes, the coturn static-auth-secret>
OGM_TURN_URLS=turn:<tailnet-host>:3478?transport=udp,turn:<tailnet-host>:3478?transport=tcp
```

The browser would receive only short-lived derived credentials, minted by the API at join — a route that does not exist
yet and belongs to the ticket that adopts TURN. The static secret never enters a bundle [O; it is also why this is never
a `VITE_*` value]. If TURN is never adopted, none of these exist and the client uses the STUN
list alone.

## 11. Risks

1. **The ticket's framing overpromises.** #498 says "measure ... and add WebRTC", and a reader will expect input latency
   to fall. On the current path ~120 ms of the peer's own-input latency is the host-authoritative design (§3.3), which
   N2 removes and N4 does not. The PR body and the workpad must say so, or the acceptance run will "fail" a change that
   is behaving correctly.
2. **TURN is unprovisionable today.** Funnel cannot carry UDP, so a symmetric-NAT pair falls back to the relay —
   permanently, until the operator opens a port. The selector must therefore never prefer WebRTC on a measurement taken
   *before* the pair is connected, and the fallback has to be a first-class path rather than an error branch.
3. **A promoted pair can hide a broken event path.** Events stay on the relay in this design, so a pair promoted while
   the room socket is unhealthy would silently lose rules-relevant messages. The demote rule "any event channel failure
   demotes" only works if the switchboard watches the *relay's* event delivery too; §7.5's last row covers it.
4. **The input rate cap has no headroom.** One input per 60 Hz step against a 60/s bucket; a burst of three (a 50 ms
   frame) fits, a sustained 61/s does not. N2's 30 Hz × 3-tick window halves the count and is the real fix; N4 must not
   add a second per-step message, or a healthy room starts dropping inputs.
5. **Snapshot fan-out is the bandwidth, not the inputs** (§3.2): 169 KiB/s of the 255 at four seats. Per-seat authority
   plus a mesh is what reduces it. If N4 ships a mesh for inputs but not for state, the bandwidth claim is empty.
6. **Test hermeticity.** Any real `RTCPeerConnection` in CI is a flake source (no networking, no ICE). §7 injects a fake
   peer connection and a fake clock; a test that reaches for the browser API must be `test:browser` and skipped when
   unavailable.
7. **Mid-epoch switching is a diagnostics event, not a state change.** N1 is explicit that a switch without a
   `net.transport` notice is a bug. N4 must emit it before the first byte travels on the new path, or two seats disagree
   about which path carried a message.
8. **iOS Safari keeps the app backgrounded for a long time.** A data channel that goes stale silently while the tab is
   hidden looks like a demotion to the selector and hides the real cause; `connectedMs` and a `closed(reason)` are the
   fields that let N6 tell those apart.

## 12. Open questions, with the default this document takes

| Question | Default | Why |
| --- | --- | --- |
| Does N4 need TURN to be useful? | No. STUN-only first; TURN is a later operator decision (§8) | The zero-cost deployment cannot expose UDP |
| Do events ride the promoted pair? | No; they stay on the relay | One authority for rules-relevant messages, no dual-receive dedupe (§4.2) |
| Does `state` get its own data channel? | No; it shares `input` with a tag byte | Both are latest-wins; one channel keeps the SCTP stream count at 1 |
| Is WebRTC attempted for every pair, or only for the host? | Every pair (mesh), decided per pair | A cable or a LAN pair between two peers can be better than the host's uplink (§3.2) |
| Who is the offerer? | The lower seat id | Deterministic, no glare handling |
| When does the relay's ping run at 1 Hz? | Only while `phase === 'playing'` and a pair is unsettled | The room caps `ping` at 10/s; 1 Hz × 4 seats is well inside it |
| Does N4 introduce a flag or an overlay? | No | §8.2's rule: no chrome, and no debug surface in a published build |
| Does N4 change the room protocol? | No | N3 owns `net.signal`/`net.transport`; N4 only consumes them (§4.5) |
| Does N4 need a new dependency? | No | Native `RTCPeerConnection`; the selector and stats are local code |

## 13. What the rewritten #498 must not do

- Do not put the transport inside the game iframe or change a bridge envelope.
- Do not switch a pair without a `net.transport` notice.
- Do not attempt a second time in the same epoch after a failed pair.
- Do not move events off the relay without a dual-receive window and a dedupe key.
- Do not add a CSS/UI surface, a query flag, or an overlay (that is #499).
- Do not buy, provision or hard-code a TURN service or key.
- Do not claim a latency win from the transport; the win is measured legs, tails and fan-out (§3.3).
